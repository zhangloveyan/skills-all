# 任务接入

## 原则

- 接受一句自然语言描述，由 Codex内部模板化，禁止要求用户填写长模板。
- 采用能够可靠完成目标的最小充分方案。
- 初判只做最低必要定位，详细分析必须经过第一次确认。
- 编码前收敛所有当前可发现的关键选择，并明确“待确认事项：无”。
- 对用户输出最小充分内容；能用一句话完整说明时只用一句。

## 工作流

### 1. 自动模板化与初判

1. 读取适用的 `AGENTS.md` 和 `references/task-types.md`。
2. 判断任务是否只有一个可验证结果；需要拆分时给出最小任务序列。
3. 只做判断规模所需的只读定位，避免在确认前展开完整审计。
4. 在内部建立任务卡：
   - 目标、类型和风险。
   - 任务规模。
   - 初步调研、改动和验证范围。
   - 外部调研目标、必要性和范围。
   - 预计消耗等级与主要来源。
   - 交付物和初始待确认事项。
5. 用简短摘要请求第一次确认。

默认摘要：

```text
目标：
规模与消耗：
调研范围：
预计改动：
验证范围：
外部调研：
交付物：
待确认：
```

纯问答、简单解释和明确只读查询可以合并初判与回答。

### 2. 详细分析与收敛

1. 第一次确认后，只在已批准范围内详细读取代码、文档、Git、日志和环境。
2. 外部调研只执行已确认的目标和范围。
3. 核对现有行为、目标行为、调用链、兼容影响、关键实现路径和验证方式。
4. 集中提出所有当前可发现且会影响结果的选择，用户回答后继续分析，直到关键待确认事项归零。
5. 输出最终方案：已确认事实、修改文件、核心逻辑、兼容与风险、针对性测试、验收标准、范围、预计消耗，并写明 `待确认事项：无`。
6. 中大型任务按适用规则先确认文档位置并保存方案。
7. 请求第二次确认。

### 3. 执行与验证

1. 用户明确确认最终方案后才执行状态变更。
2. 严格按确认范围实施，达到验收标准后结束。
3. 默认只运行与修改内容直接相关的测试；全量测试必须由用户明确要求。
4. 范围需要实质扩大时，说明原因、增量范围和新增消耗并重新确认。

### 4. 执行中新事实

执行阶段遇到前期客观无法发现的新事实时，在相关决策点暂停并说明：

```text
新事实：
无法提前发现的原因：
对方案的影响：
修订范围：
新增消耗：
需要确认：
```

前期分析本应发现的问题返回详细分析阶段处理。

## 范围与拆分

- 同一缺陷的分析、最小实现、针对性测试和本次 Diff 审查可以保留在同一任务。
- 独立功能、环境切换、风险升级、部署和事故通常使用独立任务。
- 当前标题无法描述唯一结果时停止扩展并建议新任务。

## 长任务

出现回合过长、上下文压缩、重复纠正、方案反复或阶段变化时调用 `$task-handoff`，交接内容由 Codex自动生成。
